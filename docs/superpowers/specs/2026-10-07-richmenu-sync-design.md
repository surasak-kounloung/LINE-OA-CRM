# หน้า Rich Menu ใน backoffice และการ sync ไปทุก OA (เฟส 2A) — Design Spec

วันที่: 2026-10-07
สถานะ: ผู้ใช้อนุมัติแล้ว (แก้กติกาตรวจรูปในข้อ 3 หลังอนุมัติ ตามหลักฐานจาก LINE จริง)
ต่อจาก: `docs/superpowers/specs/2026-10-07-multi-oa-webhook-design.md` (เฟส 1)

## 1. เป้าหมาย

ให้ทีมแก้ Rich Menu ที่เดียวใน `/backoffice` แล้วกด sync ให้ทุก LINE OA มีเมนูชุดเดียวกัน
โดยการแก้เมนูต้องไม่ทำให้ลูกค้าที่ถูกผูกเมนูรายคนหลุดจากเมนูของตัวเอง

### สภาพปัจจุบัน (สำรวจเมื่อ 2026-10-07 จาก OA ทดสอบ "VSQ CRM Test")

- มี Rich Menu ที่สร้างผ่าน Messaging API 6 อัน ตามระดับสมาชิก: Default (ตั้งเป็นเมนูเริ่มต้น), V Member, V Bronze, V Silver, V Gold, V Platinum
- ทั้ง 6 อันขนาด 2500x1686 และมีพื้นที่กดเหมือนกัน 4 ช่อง ต่างกันที่รูป
- โปรเจกต์ CRM LIFF (`vsq-crm/CRM-LINE-Liff-App/vsq_crm_project`) เป็นผู้ผูกเมนูให้ลูกค้ารายคนตอนสมัครสมาชิก โดยใช้ ID ของเมนูจาก `.env` ของมันเอง และรู้จัก OA บัญชีเดียว
- แอปนี้ยังไม่มีโค้ดเกี่ยวกับ Rich Menu

### งานทั้งหมดของเฟส 2 แบ่งเป็น 2 ช่วง

| ช่วง | เนื้องาน | เอกสาร |
|---|---|---|
| 2A | หน้า Rich Menu ใน `/backoffice` และการ sync ชุดเมนูไปทุก OA | เอกสารนี้ |
| 2B | API ให้ CRM แจ้งระดับสมาชิก, การผูกเมนูรายคนบนทุก OA, การย้ายลูกค้าออกจากเมนูเดิมของ OA เดิม, การแก้โปรเจกต์ CRM | spec แยก เขียนหลัง 2A เสร็จ |

### สิ่งที่ผู้ใช้ยืนยันแล้ว

- OA ใหม่ต้องมีเมนูครบชุดตามระดับสมาชิกเหมือน OA เดิม
- OA ทั้ง 3 บัญชีและ LIFF ของ CRM อยู่ใต้ Provider เดียวกัน
- แอปนี้เป็นระบบเดียวที่คุยกับ LINE เรื่อง Rich Menu ส่วน CRM จะเรียก API ของแอปนี้ (2B)
- รูปเมนูใส่เป็น URL ของรูปที่ฝากบน WordPress
- กำหนดพื้นที่กดด้วยตารางตัวเลขพร้อมภาพซ้อนบนรูป
- ผู้ใช้เป็นผู้ทดลอง sync กับ LINE จริงบน staging งานนี้ส่งมอบด้วยเทสต์อัตโนมัติ

### สมมติฐาน

- ทุกระดับใช้พื้นที่กดชุดเดียวกัน ต่างกันที่รูปเท่านั้น (ตรงกับเมนูปัจจุบัน)
- ระดับสมาชิกเป็นชุดเดียวกันทุก OA

## 2. ขอบเขต

ทำ:
- ไฟล์ข้อมูลใหม่ `data/richmenu.json` และการตรวจข้อมูลก่อนบันทึก
- ตรวจรูปจาก URL ตอนบันทึก (ชนิดไฟล์ ขนาดภาพ น้ำหนักไฟล์)
- หน้า "Rich Menu" ใน `/backoffice`
- การอ่านสถานะเมนูของแต่ละ OA จาก LINE และการ sync ทีละ OA
- เทสต์ฝั่ง server ด้วย `node --test`
- อัปเดต `CLAUDE.md`, `README.md`

ไม่ทำ (อยู่ช่วง 2B):
- API ให้ระบบอื่นแจ้งระดับสมาชิกของลูกค้า และการผูกเมนูรายคน
- การ sync OA ที่มีเมนูซึ่งระบบอื่นสร้างไว้ (OA เดิม)
- การแก้โปรเจกต์ CRM

ไม่ทำ (ไม่มีแผน):
- พื้นที่กดต่างกันในแต่ละระดับ
- เมนูหลายแท็บ (rich menu switch) และ action ชนิดอื่นนอกจากส่งข้อความกับเปิดลิงก์
- อัปโหลดไฟล์รูปเข้าเซิร์ฟเวอร์
- ลากเมาส์วาดกรอบบนรูป
- เทสต์ฝั่ง React

## 3. ข้อมูล `data/richmenu.json`

เป็น object เดียว บันทึกผ่าน `services/dataStore.js` เหมือนไฟล์อื่น (เขียนแบบ atomic, สำรอง 20 รุ่น)

```json
{
  "size": { "width": 2500, "height": 1686 },
  "chatBarText": "Menu",
  "selected": true,
  "areas": [
    { "x": 1596, "y": 0, "width": 904, "height": 1084, "action": { "type": "uri", "uri": "https://liff.line.me/2007605538-yPqjO4RW" } },
    { "x": 0, "y": 1082, "width": 833, "height": 604, "action": { "type": "message", "text": "บริการทั้งหมด" } },
    { "x": 833, "y": 1082, "width": 833, "height": 604, "action": { "type": "message", "text": "โปรโมชั่นล่าสุด" } },
    { "x": 1666, "y": 1082, "width": 833, "height": 604, "action": { "type": "message", "text": "ตารางแพทย์" } }
  ],
  "menus": []
}
```

ค่าข้างบนคือไฟล์เริ่มต้นที่ commit เข้า repo: พื้นที่กด 4 ช่องของเมนูปัจจุบัน และยังไม่มีเมนูในรายการ
ผู้ใช้เพิ่มเมนูของแต่ละระดับเองหลังอัปโหลดรูปขึ้น WordPress

รายการใน `menus`:

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `key` | string | รหัสของระดับ เช่น `default`, `gold` ใช้ตั้งชื่อ alias บน LINE ไม่ซ้ำ |
| `label` | string | ชื่อที่แสดงใน backoffice |
| `image` | string URL | รูปของเมนูนี้ |
| `isDefault` | boolean | เมนูเริ่มต้นที่ลูกค้าทุกคนเห็นเมื่อไม่ได้ถูกผูกเมนูรายคน |

`dataStore` แยก `richmenu` ออกจากรายชื่อเนื้อหาของบอท (`DATA_NAMES`) เพื่อให้ `getAll()` และตาราง trigger ไม่เปลี่ยน

### กติกาตรวจข้อมูล (`validateRichMenu` ใน `services/validate.js`)

| ฟิลด์ | กติกา |
|---|---|
| `size.width` | จำนวนเต็ม 800–2500 |
| `size.height` | จำนวนเต็มตั้งแต่ 250 และ `width / height` ต้องไม่น้อยกว่า 1.45 |
| `chatBarText` | 1–14 ตัวอักษร |
| `selected` | true/false |
| `areas` | 1–20 รายการ |
| `areas[i].x`, `.y` | จำนวนเต็มตั้งแต่ 0 |
| `areas[i].width`, `.height` | จำนวนเต็มตั้งแต่ 1 และกรอบต้องไม่เลยขอบของ `size` |
| `areas[i].action.type` | `message` หรือ `uri` |
| `action.text` (message) | 1–300 ตัวอักษร |
| `action.uri` (uri) | 1–1000 ตัวอักษร ขึ้นต้นด้วย `https://`, `http://`, `line://` หรือ `tel:` |
| `menus` | 0–20 รายการ |
| `menus[i].key` | `a-z`, `0-9`, `-` ยาว 1–20 ตัว ไม่ซ้ำ |
| `menus[i].label` | 1–50 ตัวอักษร |
| `menus[i].image` | URL ขึ้นต้นด้วย `https://` |
| `menus[i].isDefault` | true/false และถ้ามีเมนูอย่างน้อย 1 อัน ต้องมีเมนูเริ่มต้น 1 อันพอดี |

ข้อความใน `action.text` ไม่บังคับว่าต้องเป็น trigger ที่มีอยู่ เพราะข้อความบางอย่างอาจให้ระบบอื่นตอบ

รูปแบบ error เหมือนไฟล์อื่น: `[{ path, message }]` โดย `path` เทียบกับ object ราก เช่น `areas[1].action.text`, `menus[2].image`, `chatBarText`

### การตรวจรูป

ทำตอน `PUT` เฉพาะเมนูที่ URL รูปต่างจากที่บันทึกไว้ (ถ้า `size` เปลี่ยนให้ตรวจทุกเมนู) และทำกับทุกเมนูอีกครั้งตอน sync

- โหลดรูปได้ภายใน 15 วินาที
- เป็น JPEG หรือ PNG (ดูจากเนื้อไฟล์ ไม่ใช่นามสกุล)
- กว้าง 800–2500 พิกเซล สูงตั้งแต่ 250 พิกเซล
- สัดส่วนกว้างต่อสูงตรงกับ `size` (คลาดเคลื่อนได้ไม่เกิน 1%) และไม่น้อยกว่า 1.45
- น้ำหนักไม่เกิน 1 MB (1,048,576 ไบต์)

รูปไม่ต้องมีขนาดเท่ากับ `size`: เมนูปัจจุบันบน LINE ประกาศขนาด 2500x1686 แต่รูปที่อัปโหลดไว้จริงคือ 1200x810 (ตรวจจาก OA ทดสอบเมื่อ 2026-10-07) LINE ย่อ/ขยายรูปให้เอง `size` จึงเป็นเพียงพิกัดอ้างอิงของพื้นที่กด

ตัวตนของรูปคือ URL: ถ้าเปลี่ยนเนื้อรูปโดยทับไฟล์ที่ URL เดิม แอปจะไม่ถือว่าเมนูเปลี่ยน ต้องใช้ URL ใหม่

ความปลอดภัย: เซิร์ฟเวอร์โหลด URL ที่แอดมินกรอก จึงรับเฉพาะ `https://` และไม่รับ host ที่เป็น `localhost` หรือเลข IP

## 4. ชื่อบน LINE

| สิ่ง | รูปแบบ | ตัวอย่าง |
|---|---|---|
| ชื่อเมนู (`name`) | `vsq\|<key>\|<hash>` | `vsq\|gold\|3f9a1c2b7d4e5f60` |
| alias | `vsq-<key>` | `vsq-gold` |

- `<hash>` คือ 16 ตัวแรกของ SHA-256 ของ `size`, `chatBarText`, `selected`, `areas` และ URL รูปของเมนูนั้น ถ้าค่าใดเปลี่ยน hash จะเปลี่ยน
- เมนูที่ชื่อขึ้นต้นด้วย `vsq|` คือ "เมนูของแอปนี้" นอกนั้นคือ "เมนูของระบบอื่น"
- alias คือสิ่งที่ระบบอื่นจะใช้อ้างถึงเมนูของแต่ละระดับใน 2B เพราะ ID ของเมนูเปลี่ยนทุกครั้งที่แก้ แต่ alias คงเดิม
- แอปไม่เก็บสถานะของ LINE ไว้ในไฟล์ ทุกครั้งอ่านจาก LINE จริง

## 5. สถานะของแต่ละ OA

อ่านจาก LINE 3 อย่าง: รายการเมนู, รายการ alias, ID ของเมนูเริ่มต้น แล้วเทียบกับ `data/richmenu.json`

| สถานะ | เงื่อนไข | sync ได้ |
|---|---|---|
| `error` | เรียก LINE ไม่สำเร็จ | ไม่ได้ |
| `blocked` | OA มีเมนูของระบบอื่นอย่างน้อย 1 อัน | ไม่ได้ |
| `empty` | `menus` ในข้อมูลว่าง | ไม่ได้ |
| `out-of-date` | มีอย่างน้อยหนึ่งข้อที่ไม่ตรง (ดูด้านล่าง) | ได้ |
| `in-sync` | ตรงทุกข้อ | ไม่จำเป็น |

"ตรง" หมายถึงครบทุกข้อ:
- ทุก `key` มี alias `vsq-<key>` ชี้ไปที่เมนูของแอปนี้ซึ่งชื่อตรงกับ hash ปัจจุบัน
- ไม่มี alias `vsq-*` ของ `key` ที่ถูกลบออกจากรายการแล้ว
- ไม่มีเมนูของแอปนี้ที่ไม่มี alias ชี้ (เมนูค้าง)
- เมนูเริ่มต้นของ OA คือเมนูของ `key` ที่ `isDefault`

รายละเอียดต่อ `key` ที่ส่งให้หน้าจอ: `ok`, `missing` (ยังไม่มี alias), `outdated` (hash ไม่ตรง)

OA ที่ `blocked` ใน 2A คือ OA เดิม เพราะเมนู 6 อันของมันยังถูก CRM ผูกให้ลูกค้าด้วย ID อยู่ การย้ายเป็นงานของ 2B
เมนูที่สร้างใน LINE Official Account Manager มองไม่เห็นผ่าน API จึงไม่นับ และจะถูกเมนูเริ่มต้นที่ตั้งผ่าน API บังตามลำดับความสำคัญของ LINE

## 6. ขั้นตอน sync ของหนึ่ง OA

ทำตามลำดับนี้ ทุกขั้นคำนวณจากสถานะจริงบน LINE จึงกดซ้ำหลังล้มเหลวได้และจะทำต่อจากจุดที่ค้าง

1. อ่านสถานะ ถ้าเป็น `error`, `blocked` หรือ `empty` ให้หยุดและรายงานเหตุผล ถ้าเป็น `in-sync` ให้จบโดยไม่เรียกคำสั่งเขียนใด
2. โหลดและตรวจรูปของทุกเมนู ถ้ามีรูปไม่ผ่านให้หยุดก่อนแตะ LINE
3. สำหรับแต่ละ `key` ที่เป็น `missing` หรือ `outdated`: สร้างเมนูใหม่ อัปโหลดรูป แล้วชี้ alias `vsq-<key>` ไปที่เมนูใหม่ (สร้าง alias ถ้ายังไม่มี)
4. ลบ alias `vsq-*` ของ `key` ที่ไม่อยู่ในรายการแล้ว
5. หาเมนูค้าง คือเมนูของแอปนี้ที่ไม่มี alias ชี้ แล้วส่งคำสั่งย้ายลูกค้าเป็นชุดเดียว:
   - เมนูค้างที่ `key` ยังอยู่ในรายการ: ย้ายลูกค้าทุกคนไปเมนูปัจจุบันของ `key` นั้น
   - เมนูค้างที่ `key` ถูกลบแล้ว: ยกเลิกการผูก ลูกค้าจะกลับไปเห็นเมนูเริ่มต้น
6. รอผลการย้าย โดยถามสถานะทุก 1 วินาที ไม่เกิน 30 ครั้ง
7. ตั้งเมนูเริ่มต้นของ OA ให้เป็นเมนูของ `key` ที่ `isDefault` ถ้ายังไม่ใช่
8. ลบเมนูค้าง เฉพาะเมื่อขั้นที่ 6 จบด้วย "สำเร็จ"

กติกาที่ต้องเป็นจริงเสมอ:
- แอปไม่ลบ ไม่แก้ และไม่ย้ายลูกค้าออกจากเมนูของระบบอื่น
- ไม่ลบเมนูใดก่อนที่ลูกค้าของเมนูนั้นจะถูกย้ายสำเร็จ
- ไม่ลบเมนูที่เป็นเมนูเริ่มต้นอยู่ (ขั้นที่ 7 มาก่อนขั้นที่ 8)
- ส่งคำสั่งย้ายลูกค้าไม่เกิน 1 ครั้งต่อ OA ต่อการ sync หนึ่งรอบ และไม่ส่งถ้าไม่มีเมนูค้าง
- sync พร้อมกันได้ครั้งละ 1 งานทั้งแอป

เมนูที่สร้างแล้วแต่อัปโหลดรูปไม่สำเร็จจะไม่มี alias ชี้ จึงกลายเป็นเมนูค้างและถูกเก็บกวาดในรอบถัดไป

## 7. API (อยู่ใต้ `/api/admin` ต้องมี token ของแอดมิน)

| Method | Path | ทำอะไร |
|---|---|---|
| `GET` | `/richmenu` | คืนข้อมูลใน `data/richmenu.json` |
| `PUT` | `/richmenu` | ตรวจข้อมูล ตรวจรูปที่ URL เปลี่ยน แล้วบันทึก ผิดพลาดคืน `400 { error, errors }` |
| `GET` | `/richmenu/status` | คืนสถานะของทุก OA ตามข้อ 5 |
| `POST` | `/richmenu/sync/:channelId` | sync หนึ่ง OA ตามข้อ 6 คืนรายงานว่าทำขั้นใดไปบ้าง |

- `status` คืน array ของ `{ id, name, state, message, menus: [{ key, label, state }], staleCount, removedKeys: [key], foreignMenus: [ชื่อ] }`
- `sync` คืน `{ id, name, ok, steps: [ข้อความ], message }` ถ้ามีงาน sync อื่นทำอยู่คืน `409`
- หน้าจอ sync ทีละ OA หนึ่ง request ต่อหนึ่ง OA เพื่อไม่ให้ request เดียวนานเกิน timeout ของ nginx และ Cloudflare
- error จาก LINE ถูกสรุปเป็นข้อความ, HTTP status และ error body ไม่ log และไม่ส่ง object ของ SDK ออกไปทั้งก้อน

## 8. หน้า "Rich Menu" ใน `/backoffice`

เพิ่มลิงก์ในแถบข้าง หน้าเดียว ไม่มีหน้าแก้ไขย่อย ใช้ `useResource("richmenu")` และแถบบันทึกเดิม

1. **ตั้งค่าร่วม** — ข้อความบนแถบเมนู (ไม่เกิน 14 ตัวอักษร), เปิดเมนูค้างไว้เมื่อเข้าแชต, ขนาดเมนู
2. **พื้นที่กด** — ภาพตัวอย่างพร้อมกรอบหมายเลขซ้อนบนรูป (เลือกได้ว่าจะดูบนรูปของเมนูใด) และตาราง: x, y, กว้าง, สูง, ชนิด (ส่งข้อความ / เปิดลิงก์), ค่า ช่องส่งข้อความเลือกจาก trigger ที่มีอยู่จริง หรือเลือก "พิมพ์เอง"
3. **เมนูตามระดับ** — ตาราง: รหัส, ชื่อ, URL รูป, รูปย่อ, ปุ่มเลือกเมนูเริ่มต้น, ลบ และปุ่มเพิ่มเมนู
4. **สถานะ LINE OA** — แต่ละ OA แสดงสถานะ รายละเอียดต่อระดับ และปุ่ม "Sync" พร้อมปุ่ม "Sync ทุก OA ที่ sync ได้" และปุ่มรีเฟรช

พฤติกรรม:
- ปุ่ม sync กดไม่ได้เมื่อมีการแก้ไขที่ยังไม่บันทึก หรือสถานะของ OA นั้นไม่ใช่ `out-of-date`
- ก่อน sync มีหน้าต่างยืนยันที่สรุปว่าจะสร้างเมนูใด ลบเมนูของระดับใด และลูกค้าของระดับที่ถูกลบจะกลับไปเห็นเมนูเริ่มต้น
- หลัง sync แสดงรายงานขั้นตอนและโหลดสถานะใหม่
- OA ที่ `blocked` แสดงชื่อเมนูของระบบอื่นที่พบ และข้อความว่าต้องรอช่วง 2B

## 10. การจัดการข้อผิดพลาด

| กรณี | ผล |
|---|---|
| ข้อมูลไม่ผ่านกติกา | `400` พร้อมรายการ error ต่อช่อง ไม่บันทึก |
| โหลดรูปไม่ได้ หรือรูปไม่ผ่าน ตอนบันทึก | `400` ที่ `menus[i].image` ไม่บันทึก |
| รูปไม่ผ่านตอน sync | หยุดก่อนแตะ LINE รายงานว่าเมนูใด |
| LINE ปฏิเสธระหว่าง sync | หยุดที่ขั้นนั้น รายงานขั้นที่ทำไปแล้วและ error ของ LINE กดซ้ำได้ |
| การย้ายลูกค้ายังไม่เสร็จใน 30 วินาที หรือ LINE แจ้งว่าล้มเหลว | ไม่ลบเมนูค้าง รายงานให้กด sync อีกครั้งภายหลัง |
| LINE จำกัดจำนวนครั้ง (429) | รายงานข้อความของ LINE กดซ้ำภายหลังได้ |
| มีงาน sync อื่นทำอยู่ | `409` |
| `channelId` ไม่มีในรายชื่อ OA | `404` |

## 11. การทดสอบ

ใช้ `node --test` ไม่เพิ่ม dependency เทสต์เดิม 94 ข้อต้องผ่านทั้งหมด LINE ถูกแทนด้วยตัวจำลองในหน่วยความจำที่เก็บเมนู alias เมนูเริ่มต้น และการผูกลูกค้า

- `dataStore`: อ่าน/เขียน `richmenu` ได้ และ `getAll()` ยังคืน 4 ชุดเดิม
- `validateRichMenu`: ทุกกติกาในข้อ 3 ทั้งกรณีผ่านและไม่ผ่าน
- `imageInfo`: JPEG และ PNG ที่ถูกต้อง, ไฟล์ชนิดอื่น, ไฟล์ขาด
- `richMenuImages`: โหลดไม่ได้, หมดเวลา, รูปเล็กกว่าเมนูแต่สัดส่วนตรง (ต้องผ่าน), สัดส่วนไม่ตรง, กว้างหรือสูงนอกช่วง, เกิน 1 MB, host ต้องห้าม, ไม่ใช่ `https://`
- `richMenuPlan`: hash เปลี่ยนเมื่อค่าที่เกี่ยวข้องเปลี่ยนและไม่เปลี่ยนเมื่อเปลี่ยน `label`, สถานะทุกแบบในข้อ 5
- `richMenuSync` กับ LINE จำลอง:
  - OA ว่าง → ได้เมนูครบ มี alias ครบ ตั้งเมนูเริ่มต้นถูก
  - sync ซ้ำทันที → ไม่เรียกคำสั่งเขียนใดเลย
  - แก้พื้นที่กด → ทุกเมนูถูกแทน ลูกค้าที่ผูกอยู่ย้ายตาม เมนูเก่าถูกลบ
  - เปลี่ยนรูปของระดับเดียว → แทนเฉพาะระดับนั้น
  - ลบระดับ → ลูกค้าของระดับนั้นถูกยกเลิกการผูก alias และเมนูถูกลบ
  - เปลี่ยนเมนูเริ่มต้น
  - ล้มเหลวที่แต่ละขั้น (สร้าง, อัปโหลด, alias, ย้าย, ตั้งเมนูเริ่มต้น, ลบ) แล้ว sync ซ้ำ → จบที่สถานะถูกต้อง ไม่มีลูกค้าหลุด ไม่มีเมนูค้าง
  - การย้ายยังไม่เสร็จหรือล้มเหลว → ไม่ลบเมนูค้าง
  - OA ที่มีเมนูของระบบอื่น → ไม่เรียกคำสั่งเขียนใดเลย
- `richMenuRoute`: ต้องมี token, `GET`/`PUT`, error ของรูป, `status`, `sync`, `409`, `404`

ส่วนที่เทสต์อัตโนมัติไม่ครอบคลุม: `services/lineRichMenuApi.js` (ตัวเชื่อมกับ SDK) และหน้า React
ตัวเชื่อมจะถูกลองกับ OA ทดสอบเฉพาะคำสั่งอ่านอย่างเดียว (รายการเมนู, alias, เมนูเริ่มต้น, ตรวจ object ของเมนูโดยไม่สร้าง) ส่วนคำสั่งเขียนผู้ใช้ทดลองบน staging

## 12. ขั้นตอนนำขึ้นใช้งานและทดลอง (ผู้ใช้ทำ)

1. Deploy ขึ้น staging ตามหัวข้อ Deploying ของ `CLAUDE.md` รวมถึง `npm run admin:build` และ restart
2. อัปโหลดรูปเมนูของแต่ละระดับขึ้น WordPress (สัดส่วนเดียวกับเมนู เช่น 1200x810 หรือ 2500x1686 ไม่เกิน 1 MB)
3. เปิดหน้า Rich Menu เพิ่มเมนูของแต่ละระดับ วาง URL รูป เลือกเมนูเริ่มต้น แล้วบันทึก
4. ดูสถานะ: OA ใหม่ควรเป็น `out-of-date` และ OA เดิมควรเป็น `blocked`
5. กด sync OA ใหม่หนึ่งบัญชี แล้วเปิดแชตของ OA นั้นในโทรศัพท์เพื่อดูเมนูและลองกดทุกช่อง
6. แก้ข้อความบนแถบเมนูแล้ว sync อีกครั้ง เพื่อทดลองการแทนเมนูและการย้ายลูกค้า

สิ่งที่ต้องสังเกตจาก LINE จริงและแจ้งกลับ:
- LINE รับรูปที่โหลดจาก WordPress หรือไม่
- sync ที่มีการแทนเมนูทำซ้ำได้กี่ครั้งต่อชั่วโมงก่อนที่ LINE จะตอบ 429

ถอยกลับ:
- กลับไปใช้เมนูรุ่นก่อน: แก้ข้อมูลกลับเป็นค่าเดิมแล้ว sync อีกครั้ง (รุ่นก่อนหน้าของไฟล์อยู่ใน `data/backup/`)
- ถอดเมนูของแอปนี้ออกจาก OA ทั้งหมด: ไม่มีปุ่มใน 2A ต้องเรียก API ของ LINE เอง คือยกเลิกเมนูเริ่มต้น (`DELETE /v2/bot/user/all/richmenu`) แล้วลบเมนูที่ชื่อขึ้นต้นด้วย `vsq|` การตั้งเมนูใน LINE Official Account Manager อย่างเดียวไม่พอ เพราะเมนูเริ่มต้นที่ตั้งผ่าน API มีลำดับสูงกว่า

## 13. เกณฑ์ว่าสำเร็จ

- แก้พื้นที่กดหรือรูปในหน้า Rich Menu ครั้งเดียว แล้ว sync ทำให้ทุก OA ที่ sync ได้มีเมนูตรงกัน
- sync ซ้ำโดยไม่มีการแก้ไขไม่เปลี่ยนอะไรบน LINE
- การแก้เมนูไม่ทำให้ลูกค้าที่ถูกผูกเมนูรายคนหลุด (พิสูจน์ด้วยเทสต์กับ LINE จำลอง)
- OA เดิมและเมนูของระบบอื่นไม่ถูกแตะ
- `npm test` ผ่านทั้งหมด

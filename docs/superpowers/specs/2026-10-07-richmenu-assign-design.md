# ผูก Rich Menu ตามระดับสมาชิกบนทุก OA และย้าย OA เดิม (เฟส 2B) — Design Spec

วันที่: 2026-10-07
สถานะ: รอผู้ใช้ตรวจ
ต่อจาก: `docs/superpowers/specs/2026-10-07-richmenu-sync-design.md` (เฟส 2A)

## 1. เป้าหมาย

ให้ลูกค้าเห็น Rich Menu ตามระดับสมาชิกของตัวเองบนทุก LINE OA โดยระบบ CRM แจ้งระดับมาที่แอปนี้
และให้ OA เดิมย้ายจากเมนูชุดเก่าที่ CRM ผูกด้วย ID มาใช้เมนูชุดที่แอปนี้ดูแล

### สภาพปัจจุบัน

- 2A: แอปนี้ sync ชุดเมนูไป OA ได้ แต่ยังไม่มีใครถูกผูกเมนูตามระดับ และ OA เดิมถูกกันไว้ (`blocked`)
- โปรเจกต์ CRM LIFF (`vsq-crm/CRM-LINE-Liff-App/vsq_crm_project`):
  - รู้ `member_level_name` ทุกครั้งที่ลูกค้าเปิด LIFF (`src/app/api/auth/route.ts`, `src/app/api/auth/callback/route.ts`)
  - ผูกเมนูเฉพาะตอนสมัคร (`src/app/api/user/route.ts`) โดยเรียก LINE เองด้วย `LINE_ACCESS_TOKEN` และ ID จาก `RICHMENU_MEMBER` / `RICHMENU_GOLD` / `RICHMENU_PLATINUM` (`v gold` → GOLD, `v platinum` → PLATINUM, นอกนั้น → MEMBER)
  - รู้จัก OA บัญชีเดียว

### สิ่งที่ผู้ใช้ยืนยันแล้ว

- เมนูของลูกค้าเปลี่ยนตามระดับตอนสมัคร และทุกครั้งที่เปิด LIFF
- ผูกเมนูบนทุก OA พร้อมกัน ระดับที่ไม่ตรงกับเมนูใดได้ "เมนูสำรองของสมาชิก"
- ย้าย OA เดิมแบบครั้งเดียวจบ ยอมรับช่วงสั้น ๆ ระหว่างย้ายกับสลับ CRM ที่คนสมัครใหม่เห็นเมนูเริ่มต้น
- ฝั่ง CRM ทำจากเอกสารส่งต่อ ในเซสชันของโปรเจกต์นั้น

### สมมติฐาน

- user ID ของลูกค้าเป็นค่าเดียวกันทุก OA เพราะทุก channel อยู่ใต้ Provider เดียวกัน (ผู้ใช้ยืนยัน)
- CRM เรียกแอปนี้จากฝั่งเซิร์ฟเวอร์ (Next.js route) ไม่ใช่จากเบราว์เซอร์ของลูกค้า

## 2. ขอบเขต

ทำ:
- ช่อง "ชื่อระดับจาก CRM" และ "เมนูสำรองของสมาชิก" ในข้อมูลและหน้า Rich Menu
- API ให้ CRM แจ้งระดับ: `POST /api/richmenu/assign`
- ผูกเมนูให้ลูกค้าที่เพิ่มเพื่อน OA อื่นทีหลัง (จาก webhook `follow`)
- ย้ายเมนูเดิมของ OA ที่ `blocked`: API และส่วนในหน้า Rich Menu
- เอกสารส่งต่อสำหรับโปรเจกต์ CRM
- เทสต์ฝั่ง server, อัปเดต `.env.example`, `CLAUDE.md`, `README.md`

ไม่ทำ:
- แก้โค้ดใน repo ของ CRM (ทำจากเอกสารส่งต่อ)
- เก็บรายชื่อสมาชิกหรือระดับไว้ในแอปนี้ (LINE เป็นที่เก็บว่าใครผูกเมนูไหน)
- แจ้งเตือนจากระบบ OPD เมื่อระดับเปลี่ยน
- ย้ายแบบไม่มีช่วงขาด (3 ขั้น)

## 3. ข้อมูลที่เพิ่มใน `data/richmenu.json`

เพิ่ม 2 ฟิลด์ในแต่ละรายการของ `menus`:

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `levels` | string[] | ชื่อระดับจาก CRM ที่ใช้เมนูนี้ เช่น `["V Gold"]` ว่างได้ |
| `isMemberFallback` | boolean | เมนูที่ใช้เมื่อชื่อระดับไม่ตรงกับเมนูใด |

กติกา:
- `levels`: 0–10 ชื่อต่อเมนู แต่ละชื่อ 1–50 ตัวอักษร
- การเทียบชื่อระดับ: ตัดช่องว่างหัวท้าย รวมช่องว่างซ้อน และไม่สนตัวพิมพ์เล็กใหญ่ (`" v  GOLD "` = `"V Gold"`)
- ชื่อระดับเดียวกันอยู่ได้ในเมนูเดียว (หลังเทียบตามข้อบน)
- `isMemberFallback` เป็น true ได้ไม่เกิน 1 เมนู ไม่มีก็ได้
- ไฟล์ที่บันทึกจาก 2A ไม่มีสองฟิลด์นี้: ถือเป็น `[]` และ `false` และถูกเติมให้เมื่อบันทึกครั้งถัดไป
- สองฟิลด์นี้ไม่อยู่ใน hash ของเมนู การแก้จึงไม่ทำให้ต้อง sync ใหม่

การเลือกเมนูจากชื่อระดับ:

| ชื่อระดับที่ CRM ส่งมา | ผล |
|---|---|
| ตรงกับ `levels` ของเมนูใด | ผูกเมนูนั้น |
| ไม่ตรงกับเมนูใด และมีเมนูสำรอง | ผูกเมนูสำรอง |
| ไม่ตรงกับเมนูใด และไม่มีเมนูสำรอง | ยกเลิกการผูก (ลูกค้าเห็นเมนูเริ่มต้น) |
| `null` หรือว่าง | ยกเลิกการผูก |

## 4. API ให้ CRM: `POST /api/richmenu/assign`

อยู่นอก `/api/admin` และไม่ใช้ token ของแอดมิน

- ตัวแปร `RICHMENU_API_KEY` ใน `.env`: กุญแจลับที่ CRM ต้องส่งมาใน header `Authorization: Bearer <key>` ต้องยาวอย่างน้อย 24 ตัวอักษร
- ไม่ได้ตั้งหรือสั้นเกิน → เส้นทางนี้ตอบ `503` ทุกครั้ง
- กุญแจไม่ตรง → `401` (เทียบแบบใช้เวลาคงที่)
- Body: `{ "lineUserId": "U…", "level": "V Gold" }` โดย `lineUserId` ต้องตรงรูปแบบ `U` ตามด้วยเลขฐานสิบหก 32 ตัว และ `level` เป็น string ไม่เกิน 100 ตัวอักษรหรือ `null` ผิดรูปแบบ → `400`
- สำเร็จ → `200 { "results": [{ "id", "name", "ok", "action", "menuKey", "message" }] }` หนึ่งรายการต่อ OA
  - `action`: `linked`, `unlinked` หรือ `skipped`
  - ตอบ `200` แม้บาง OA ล้มเหลว (`ok: false` ในรายการนั้น) เพื่อให้การสมัครและการ login ของ CRM ไม่ล้มเพราะเรื่องเมนู
- ข้อมูลเมนูที่บันทึกไว้ไม่ถูกต้อง (สถานะ `invalid` ของ 2A) → `200` โดยทุก OA เป็น `skipped`

การทำงานต่อหนึ่ง OA:
1. ถ้า OA นั้นยังไม่มี alias ของเมนูเริ่มต้น (`vsq-<key ของเมนูเริ่มต้น>`) แปลว่ายังไม่ได้ sync หรือยังไม่ได้ย้าย → `skipped` และ**ไม่แตะการผูกเดิมของลูกค้าบน OA นั้น**
2. หา ID ปัจจุบันของเมนูจาก alias `vsq-<key>` แล้วผูกให้ลูกค้า หรือยกเลิกการผูกตามตารางข้อ 3 ถ้า OA นั้นยังไม่มี alias ของ `key` ที่ต้องผูก (เช่น เพิ่มระดับใหม่แล้วยังไม่ได้ sync) → `ok: false` และไม่แตะการผูกเดิม
3. alias ถูกจำไว้ในหน่วยความจำต่อ OA และล้างทุกครั้งที่ OA นั้นถูก sync หรือย้าย ถ้าผูกแล้ว LINE ตอบว่าไม่พบเมนู ให้ล้าง อ่านใหม่ แล้วลองอีกหนึ่งครั้ง

แอปไม่เก็บว่าลูกค้าคนใดอยู่ระดับใด

## 5. ลูกค้าเพิ่มเพื่อน OA อื่นทีหลัง

เมื่อ webhook ของ OA หนึ่งมี event ชนิด `follow`:
1. ถ้าลูกค้ามีเมนูรายคนบน OA นั้นอยู่แล้ว ไม่ทำอะไร
2. ไล่ดู OA อื่นตามลำดับ ว่าลูกค้าถูกผูกเมนูใดอยู่ แล้วแปลง ID กลับเป็น `key` จาก alias ของ OA นั้น
3. เจอ `key` แรก → ผูกเมนูของ `key` เดียวกันบน OA ที่เพิ่งเพิ่มเพื่อน
4. ไม่เจอ → ไม่ทำอะไร (ลูกค้าเห็นเมนูเริ่มต้น และจะได้เมนูตามระดับเมื่อเปิด LIFF)

ทำแบบไม่รอผลและไม่กระทบการตอบข้อความ ข้อผิดพลาดถูก log เท่านั้น

## 6. ย้ายเมนูเดิมของ OA ที่ `blocked`

`POST /api/admin/richmenu/migrate/:channelId` (ต้องมี token ของแอดมิน)
Body: `{ "mapping": { "<richMenuId ของเมนูเดิม>": "<key>" | null } }` โดย `null` คือปล่อยลูกค้ากลับเมนูเริ่มต้น

- ต้องระบุปลายทางของเมนูเดิม**ทุกอัน**บน OA นั้น และ `key` ต้องอยู่ในรายการ ไม่ครบหรือผิด → ไม่ส่งคำสั่งใดไป LINE
- ขั้นตอนเหมือน sync ของ 2A โดยเพิ่ม:
  - ไม่หยุดเพราะมีเมนูของระบบอื่น
  - คำสั่งย้ายลูกค้าชุดเดียวกันรวมเมนูเดิมด้วย: ย้ายไปเมนูปัจจุบันของ `key` ที่เลือก หรือยกเลิกการผูก
  - หลัง LINE ย้ายสำเร็จและตั้งเมนูเริ่มต้นแล้ว: ลบ alias ของระบบอื่นที่ชี้ไปเมนูเดิม แล้วลบเมนูเดิม
- กติกาความปลอดภัยของ 2A ใช้ครบ: ไม่ลบเมนูใดก่อนย้ายลูกค้าสำเร็จ ไม่ลบเมนูเริ่มต้นก่อนตั้งอันใหม่ ล้มกลางทางแล้วส่ง mapping เดิมซ้ำได้
- ใช้ lock เดียวกับ sync (ครั้งละ 1 งานทั้งแอป)
- `status` ของ 2A เปลี่ยน `foreignMenus` จากรายชื่อเป็น `[{ richMenuId, name }]` เพื่อให้หน้าจอสร้าง mapping ได้

หลังย้าย OA นั้นจะไม่มีเมนูของระบบอื่นแล้ว จึง sync ได้ตามปกติ

## 7. หน้า Rich Menu ที่เพิ่ม

- ตาราง "เมนูตามระดับสมาชิก": ช่อง "ชื่อระดับจาก CRM" (พิมพ์คั่นด้วยจุลภาค) และปุ่มเลือก "เมนูสำรองของสมาชิก" พร้อมตัวเลือก "ไม่มี"
- OA ที่ `blocked`: ส่วน "ย้ายเมนูเดิม" แสดงเมนูเดิมทุกอัน แต่ละอันมีตัวเลือกปลายทาง (ระดับในรายการ หรือ "ปล่อยกลับเมนูเริ่มต้น") และปุ่ม "ย้ายและลบเมนูเดิม"
  - กดไม่ได้เมื่อมีการแก้ไขที่ยังไม่บันทึก หรือยังเลือกปลายทางไม่ครบ
  - หน้าต่างยืนยันบอกว่าเมนูเดิมจะถูกลบ และระบบอื่นที่ถือ ID ของเมนูเดิมจะใช้ ID นั้นไม่ได้อีก ต้องสลับ CRM ตามทันที

## 9. เอกสารส่งต่อสำหรับ CRM (สรุปเนื้อหา)

- ตัวแปรใหม่: `RICHMENU_API_URL` (เช่น `https://<โดเมนของแอปนี้>/api/richmenu/assign`) และ `RICHMENU_API_KEY`
- ตัวแปรที่เลิกใช้: `RICHMENU_DEFAULT`, `RICHMENU_MEMBER`, `RICHMENU_GOLD`, `RICHMENU_PLATINUM` และ `LINE_ACCESS_TOKEN` (ใช้เฉพาะการผูกเมนู)
- `src/app/api/user/route.ts`: แทนการเรียก LINE ด้วยการเรียก API นี้ ส่ง `member_level_name` ตามที่ได้จาก OPD โดยไม่ต้องแปลงเอง คงพฤติกรรมเดิมว่าเมนูล้มเหลวไม่ทำให้การสมัครล้ม
- `src/app/api/auth/route.ts` และ `src/app/api/auth/callback/route.ts`: หลังได้โปรไฟล์จาก OPD ให้เรียก API นี้แบบไม่รอผล มี timeout และไม่ทำให้ login ล้ม
- ตั้ง `User-Agent` ของคำขอเอง เพราะ Cloudflare หน้าเซิร์ฟเวอร์เคยบล็อก user agent เริ่มต้นของเครื่องมือฝั่งเซิร์ฟเวอร์
- ห้าม log ค่าของกุญแจ
- ขั้นตอนทดสอบบน staging และลำดับขึ้นระบบตามข้อ 11

## 10. การทดสอบ

ใช้ `node --test` ไม่เพิ่ม dependency เทสต์เดิม 176 ข้อต้องผ่านทั้งหมด LINE จำลองของ 2A ถูกขยายให้มีคำสั่งผูกลูกค้ารายคน

- กติกาของ `levels` และ `isMemberFallback`, ไฟล์แบบ 2A ที่ไม่มีสองฟิลด์
- `resolveMenuKey`: ทุกแถวของตารางข้อ 3 และการเทียบชื่อแบบไม่สนช่องว่างกับตัวพิมพ์
- ตัวผูกเมนู: ผูกทุก OA, OA ที่ยังไม่ sync ถูกข้ามและการผูกเดิมไม่ถูกแตะ, ระดับว่างยกเลิกการผูก, OA หนึ่งล้มเหลวไม่กระทบ OA อื่น, alias ที่จำไว้ถูกอ่านใหม่เมื่อเมนูถูกแทน
- `follow`: คัดลอกระดับจาก OA อื่น, ไม่ทำอะไรเมื่อมีเมนูรายคนอยู่แล้วหรือไม่พบระดับ, ข้อผิดพลาดไม่กระทบการตอบข้อความ
- ย้ายเมนูเดิม: ลูกค้าทุกคนไปถึงเมนูใหม่หรือถูกยกเลิกตาม mapping, mapping ไม่ครบไม่ส่งคำสั่งใด, alias ของระบบอื่นถูกลบก่อนเมนู, ล้มที่แต่ละขั้นแล้วส่งซ้ำ, ไม่มีลูกค้าหลุดและไม่เสียเมนูเริ่มต้น
- API: `503` เมื่อไม่ตั้งกุญแจ, `401`, `400`, รูปแบบผลลัพธ์, `migrate` ผ่าน route, lock ร่วมกับ sync
- webhook: event `follow` ถูกส่งต่อโดยไม่หน่วงคำตอบ

ไม่ครอบคลุมด้วยเทสต์อัตโนมัติ: หน้า React และคำสั่งเขียนไปยัง LINE จริง

## 11. ลำดับขึ้นระบบและสิ่งที่ต้องลองกับ LINE จริง (ผู้ใช้ทำ)

1. ทดลอง 2A บน staging ให้ผ่านก่อน
2. Deploy แอปนี้พร้อม 2B ตั้ง `RICHMENU_API_KEY` กรอกชื่อระดับของแต่ละเมนู เลือกเมนูสำรอง บันทึก แล้ว sync OA ใหม่
3. บน staging: เรียก API ด้วย user ID ของบัญชีทดสอบ แล้วดูเมนูในโทรศัพท์
4. กด "ย้ายเมนูเดิม" ของ OA เดิม
5. Deploy CRM ที่แก้ตามเอกสารส่งต่อทันที

สิ่งที่ยืนยันได้จาก LINE จริงเท่านั้น:
- LINE ยอมให้ผูกเมนูกับลูกค้าที่ยังไม่ได้เพิ่มเพื่อน OA นั้นหรือไม่ (ถ้าไม่ยอม ผลของ OA นั้นจะเป็น `ok: false` และลูกค้าได้เมนูตอนเพิ่มเพื่อนตามข้อ 5)
- LINE ยอมให้ลบเมนูที่ยังมี alias ชี้อยู่หรือไม่ (แอปลบ alias ก่อนเสมอ จึงไม่ขึ้นกับคำตอบ)
- Cloudflare ปล่อยคำขอจากเซิร์ฟเวอร์ CRM หรือไม่

## 12. เกณฑ์ว่าสำเร็จ

- CRM แจ้งระดับครั้งเดียว ลูกค้าเห็นเมนูของระดับนั้นบนทุก OA ที่ sync แล้ว
- ลูกค้าที่เลื่อนระดับเห็นเมนูใหม่หลังเปิด LIFF
- ย้าย OA เดิมแล้วไม่มีลูกค้าหลุดจากเมนูของระดับตัวเอง (พิสูจน์ด้วยเทสต์กับ LINE จำลอง)
- OA ที่ยังไม่ sync หรือยังไม่ย้าย ไม่ถูกแตะโดย API ของ CRM
- `npm test` ผ่านทั้งหมด

# ข้อความต่อท้ายบริการ ตั้งแยกต่อ LINE OA และต่อบริการ — Design Spec

วันที่: 2026-10-30
สถานะ: ผู้ใช้อนุมัติแล้ว (2026-10-30)

## 1. เป้าหมายและเหตุผล

เมื่อลูกค้ากดดูบริการ (trigger = `actionText` ของบริการ) บอทตอบด้วยรูปราคา แล้วต่อท้ายด้วยข้อความหนึ่งบรรทัดที่บอกลูกค้าว่าใครจะคุยต่อ
ตอนนี้ข้อความนี้เป็นค่าคงที่ในโค้ด (`FOLLOW_UP_TEXT = "👨‍⚕️ปรึกษาหมอได้เลย หมอตอบเองครับ"` ใน `services/messageTable.js`) และทุก OA ส่งเหมือนกัน

แต่คนตอบแชทของแต่ละ OA ไม่เหมือนกัน:

- **LINE Main** (OA 1) มีหมอตอบแชทจริง จึงใช้ "👨‍⚕️ปรึกษาหมอได้เลย หมอตอบเองครับ" ได้
- **อีก 31 OA** (หนึ่ง OA ต่อสาขา) มีพนักงานทั่วไปตอบ ถ้าบอกว่า "หมอตอบเอง" จะเป็นการบอกลูกค้าผิด ต้องใช้ "✨ สนใจโปรโมชัน ทำนัดคิว หรือสอบถามข้อมูลเพิ่มเติม สามารถแจ้งได้เลยค่ะ"
- ในอนาคตแต่ละสาขาจะใช้ข้อความของตัวเอง และอาจต่างกันในแต่ละบริการด้วย

งานนี้ย้ายข้อความนี้ออกจากโค้ดมาเป็นข้อมูลที่ **ทีมแชท** แก้เองได้ในหลังบ้าน `/backoffice` โดยปกติแก้ทีละสาขา

### สิ่งที่ผู้ใช้ยืนยันแล้ว

- ตั้งข้อความได้ 3 ระดับ ระดับที่เจาะจงกว่าชนะ: ข้อความตั้งต้น → ข้อความของ OA → ข้อความของบริการใน OA นั้น
- OA ที่ **ยังไม่ได้ตั้ง** ใช้ข้อความตั้งต้น รวมถึง OA ใหม่ที่เพิ่มใน `.env` ภายหลัง
- OA ที่ **ตั้งให้ว่าง** ไม่ส่งข้อความนี้เลย
- ข้อความแยกตามบริการตั้งได้ **ต่อสาขา** (แต่ละ OA ตั้งข้อความของบริการเดียวกันต่างกันได้)
- หน้าจอแบบ A (เลือกจากภาพตัวอย่าง): หน้ารายชื่อ OA แล้วกดเข้าไปแก้ทีละ OA
- ค่าเริ่มต้นเมื่อเปิดใช้: ข้อความตั้งต้น = ข้อความพนักงาน, OA 1 (Main) = ข้อความหมอ, OA อื่นทั้งหมดใช้ค่าตั้งต้น

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / สิ่งที่ห้ามเกิด

**เป้าหมาย**

- แต่ละ OA ส่งข้อความต่อท้ายตามที่ตั้งไว้ในหลังบ้าน บันทึกแล้วมีผลกับข้อความถัดไปทันที ไม่ต้อง restart
- ทีมแชทเห็นได้ทันทีว่าบอทของ OA นั้นจะส่งข้อความอะไรจริงในแต่ละบริการ โดยไม่ต้องไล่ระดับเอง

**ไม่ใช่เป้าหมาย**

- ข้อความของบริการที่ใช้ร่วมกันทุก OA (ระดับ "บริการ" ที่ไม่ผูก OA) — ผู้ใช้เลือกให้ตั้งต่อสาขา
- ข้อความต่อท้ายของคำตอบอื่น (โปรโมชั่น สาขา ตารางแพทย์) — มีเฉพาะคำตอบของบริการเหมือนเดิม
- สิทธิ์แยกรายคน หรือบันทึกว่าใครแก้อะไร — หลังบ้านยังใช้รหัสผ่านเดียว
- ตั้งข้อความล่วงหน้าตามวันเวลา

**สิ่งที่ห้ามเกิด** (ถึงจะทำงานได้ก็ถือว่าพลาด)

- OA หนึ่งส่งข้อความที่ตั้งไว้ให้อีก OA (เช่น สาขาส่ง "หมอตอบเอง")
- บอทเรียก `replyMessage` ด้วยรายการข้อความว่าง (`[]`) — LINE ตอบ 400 และลูกค้าไม่ได้อะไรเลย
- การแก้ข้อความของ OA หนึ่งไปทับสิ่งที่อีกคนเพิ่งบันทึกให้อีก OA
- คำตอบที่มีอยู่แล้ว (รูปราคา, trigger อื่น) เปลี่ยนไปจากเดิม นอกจากข้อความต่อท้าย

## 3. กติกาเลือกข้อความ

ทุกช่องในระดับ OA และระดับบริการอยู่ในหนึ่งใน 3 สถานะ:

| สถานะ | ความหมาย | ข้อมูลที่เก็บ |
|---|---|---|
| ใช้ค่าจากระดับบน | ระดับ OA ใช้ข้อความตั้งต้น, ระดับบริการใช้ข้อความของ OA | ไม่มี key นั้น |
| ตั้งข้อความเอง | ใช้ข้อความที่พิมพ์ | string ที่มีตัวอักษร |
| ไม่ส่ง | ไม่ส่งข้อความต่อท้าย | `""` |

ตามที่ผู้ใช้บอกไว้ตั้งแต่แรกว่า "ช่องว่าง = ไม่ส่ง" ถ้าเลือก "ตั้งข้อความเอง" แต่ปล่อยว่าง (หรือมีแต่ช่องว่าง/ขึ้นบรรทัด) จะบันทึกเป็น `""` คือ "ไม่ส่ง" และเปิดหน้าครั้งถัดไปจะแสดงเป็น "ไม่ส่ง"

ข้อความตั้งต้นเป็น string เดียว ถ้าว่างแปลว่า OA ที่ใช้ค่าตั้งต้นไม่ส่งข้อความ

ลำดับการเลือก เมื่อลูกค้าของ OA `c` กดบริการ `s`:

1. ถ้ามีค่าของบริการ `s` ใน OA `c` → ใช้ค่านั้น
2. ไม่อย่างนั้น ถ้ามีค่าของ OA `c` → ใช้ค่านั้น
3. ไม่อย่างนั้น → ใช้ข้อความตั้งต้น

ค่าที่ได้ว่างหรือมีแต่ช่องว่าง = ไม่ส่ง ไม่ไหลต่อไประดับถัดไป

คำตอบของบริการ = รูปราคา (ถ้ามี) ตามด้วยข้อความต่อท้าย (ถ้ามี) — ลำดับเดิม
ถ้าทั้งสองอย่างไม่มี (บริการไม่มีรูปราคา และ OA นั้นไม่ส่ง) บอท **ไม่ตอบ** trigger นั้นสำหรับ OA นั้น
OA อื่นที่มีข้อความต่อท้ายยังตอบ trigger เดียวกันได้ตามปกติ

## 4. ข้อมูล

ไฟล์ใหม่ `data/followups.json` อ่าน/เขียน/สำรองผ่าน `services/dataStore.js` แบบเดียวกับ `richmenu` (เพิ่มใน `EXTRA_NAMES` เพราะไม่ใช่ข้อมูลที่ใช้สร้างตาราง trigger)
ได้การเขียนแบบ atomic และสำรอง 20 เวอร์ชันใน `data/backup/` เหมือนไฟล์อื่น

```json
{
  "defaultText": "✨ สนใจโปรโมชัน ทำนัดคิว หรือสอบถามข้อมูลเพิ่มเติม สามารถแจ้งได้เลยค่ะ",
  "channels": {
    "1": { "text": "👨‍⚕️ปรึกษาหมอได้เลย หมอตอบเองครับ" },
    "3": { "services": { "botox": "💉 สอบถามราคาโบท็อกซ์สาขาเอกมัยได้เลยค่ะ", "v-safe-slim": "" } },
    "30": { "text": "" }
  }
}
```

- key ของ `channels` คือเลข OA จาก `.env` (OA แรก = `"1"`, `LINE_CHANNEL_*_<n>` = `"<n>"`) ตรงกับ `channel.id` ใน `services/channels.js` และเลขที่หน้า Rich Menu ใช้
- `text` ไม่มี = ใช้ข้อความตั้งต้น
- `services` เป็น map จาก `id` ของบริการ (ไม่ใช่ `actionText`) ไปยัง string; ไม่มี key = ใช้ข้อความของ OA
- ไฟล์ที่ commit ไปพร้อมงานนี้มีเนื้อหาตามค่าเริ่มต้นในข้อ 1 เท่านั้น: `defaultText` = ข้อความพนักงาน, `channels` = `{ "1": { "text": ข้อความหมอ } }`

### OA และบริการที่หายไป

- OA ที่ถูกเอาออกจาก `.env`: ค่าที่ตั้งไว้ยังอยู่ในไฟล์ ไม่แสดงในหน้า ถ้าเพิ่ม OA เลขเดิมกลับมา ค่าเดิมกลับมาใช้ (ผู้ใช้รับทราบแล้ว)
- ห้ามสลับเลข OA ใน `.env` — ข้อความจะไปอยู่กับสาขาอื่น ต้องเขียนไว้ใน CLAUDE.md / README และในหน้ารายชื่อ OA
- บริการที่ถูกลบ หรือถูกเปลี่ยน `id`: ค่าที่ตั้งไว้ให้ `id` เดิมในทุก OA ต้องถูกลบไปด้วย ในการบันทึกบริการครั้งนั้น
  เหตุผล: ถ้าวันหลังมีบริการใหม่ใช้ `id` เดิม จะได้ข้อความเก่าไปโดยไม่มีใครตั้ง
  หน้าแก้บริการต้องบอกใต้ช่อง `id` ว่าการเปลี่ยน `id` จะล้างข้อความต่อท้ายที่ตั้งแยกไว้ให้บริการนี้
- ระหว่างนั้น การเลือกข้อความต้องไม่ล้มถ้าเจอ `id` บริการที่ไม่มีอยู่แล้ว (ข้ามไป)

### ไฟล์หายหรือเสีย

ถ้า `data/followups.json` ไม่มี หรือไม่ใช่ JSON ที่ถูกต้อง หรือผิดกติกาในข้อ 5:

- webhook ต้องทำงานต่อ: ตอบรูปราคาตามปกติ **โดยไม่มี** ข้อความต่อท้าย และ log ข้อผิดพลาดให้เห็น (ไม่ต้อง log ซ้ำทุกข้อความจนท่วม log — วิธีจำกัดเป็นของผู้สร้าง)
- บริการที่ไม่มีรูปราคาจึงไม่ตอบในช่วงนั้น (ตามกติกา "ไม่ส่ง [] ให้ LINE")
- หน้า "ข้อความต่อท้าย" แสดงข้อผิดพลาดให้เห็นชัด
- API บันทึกของข้อความต่อท้ายปฏิเสธด้วยข้อความชัดเจน (แบบที่ route ของ Rich Menu ทำเมื่อ `richmenu.json` เสีย) และ **ห้ามสร้างไฟล์ใหม่ทับ** — ไฟล์ที่เสียต้องให้คนเข้าไปดูก่อน ไม่อย่างนั้นค่าที่ตั้งไว้ทั้งหมดจะหายเงียบ ๆ
- การบันทึกบริการยังทำได้ตามปกติ แต่ข้ามขั้นลบค่าของ `id` ที่หายไป (log ไว้) — กติกาเลือกข้อความข้าม `id` ที่ไม่มีอยู่อยู่แล้ว

## 5. กติกาตรวจข้อมูล

ตรวจทุกครั้งที่บันทึก คืน `{ path, message }[]` ภาษาไทยแบบ `services/validate.js`:

- `defaultText` และทุก `text` / ค่าใน `services` เป็น string ยาวไม่เกิน 5,000 ตัวอักษร (ข้อจำกัดของ LINE text message)
- key ของ `channels` เป็นเลขจำนวนเต็มบวกไม่มีศูนย์นำหน้า
- ค่าที่ไม่ใช่ string (เช่น `null`, ตัวเลข) ถือว่าผิด
- ข้อความถูกตัดช่องว่าง/บรรทัดว่างหัวท้ายก่อนบันทึก ข้อความที่มีแต่ช่องว่างจึงกลายเป็น `""` (ไม่ใช่ error) ช่องว่างและการขึ้นบรรทัดตรงกลางข้อความเก็บตามที่พิมพ์
- OA ที่ทั้ง `text` และ `services` ว่างหมด (ใช้ค่าจากระดับบนทุกช่อง) ถูกเอาออกจาก `channels` ไปเลย ไฟล์จะได้เก็บเฉพาะ OA ที่ตั้งอะไรไว้จริง

## 6. API หลังบ้าน (ใต้ `/api/admin`, ต้อง login เหมือน endpoint อื่น)

ทีมแชทหลายคนอาจแก้คนละสาขาพร้อมกัน จึง **ไม่ใช้ PUT ทั้งไฟล์** แบบ resource อื่น แต่บันทึกทีละส่วน:

| Method | Path | ทำอะไร |
|---|---|---|
| GET | `/followups` | ข้อมูลทั้งไฟล์ + รายชื่อ OA ที่โหลดจาก `.env` (`id`, `name` เท่านั้น — ห้ามมี token/secret) |
| PUT | `/followups/default` | body `{ "text": "..." }` แทนที่ `defaultText` อย่างเดียว |
| PUT | `/followups/channels/:id` | body `{ "text"?: "...", "services": { ... } }` แทนที่ข้อมูลของ OA นั้นทั้งก้อน ไม่แตะ OA อื่น; `text` ไม่ส่งมา = ใช้ข้อความตั้งต้น |

- `:id` ต้องเป็น OA ที่โหลดอยู่ตอนนี้ ไม่อย่างนั้นตอบ 404
- `id` บริการใน body ที่ไม่มีใน `services.json` ถูกตัดทิ้งตอนบันทึก (ไม่ใช่ error — หน้าอาจเปิดค้างไว้ตอนมีคนลบบริการ)
- ข้อมูลผิดกติกา → 400 `{ error, errors }` รูปแบบเดียวกับ resource อื่น
- บันทึกสำเร็จตอบข้อมูลล่าสุดในรูปแบบเดียวกับ GET
- แอปรันเป็น process เดียว (cache ในหน่วยความจำ เหมือน Rich Menu) การบันทึกคนละ OA จึงไม่ทับกัน ถ้าสองคนแก้ **OA เดียวกัน** พร้อมกัน คนที่บันทึกทีหลังชนะ — ยอมรับได้ เพราะทีมแชทแก้ทีละสาขา

### Preview

`GET /preview/:trigger` รับ query `channel` เพิ่ม และคืนสิ่งที่ OA นั้นจะส่งจริง รวมข้อความต่อท้าย
ถ้าไม่ส่ง `channel` ใช้ OA แรกในรายการ (Main) — ปุ่ม "ดู Flex JSON" ที่มีอยู่จึงยังได้ผลเหมือนวันนี้
ถ้า OA นั้นไม่ตอบ trigger นี้ (ไม่มีอะไรจะส่ง) หรือ `channel` ไม่ใช่ OA ที่โหลดอยู่ ตอบ 404 พร้อมข้อความที่บอกว่าเป็นกรณีไหน

`GET /triggers` ไม่เปลี่ยน: `actionText` ของทุกบริการยังเป็น trigger แม้ไม่มีรูปราคา เพราะบาง OA ยังตอบอยู่

## 7. Webhook

- การเลือกข้อความต่อท้ายทำตอนตอบ จาก OA ที่ส่ง webhook มา (`channel.id` ที่ได้จาก signature) และ `id` ของบริการที่ trigger นั้นเป็นของ
- อ่าน `followups` จาก store ทุกครั้ง (store cache ไว้แล้ว) บันทึกจากหลังบ้านจึงมีผลกับข้อความถัดไปทันที
- ตาราง trigger ยังใช้ร่วมกันทุก OA — ส่วนที่เปลี่ยนต่อ OA มีแค่ข้อความต่อท้าย
- ห้ามเรียก `replyMessage` ด้วยรายการว่าง
- จำนวนข้อความต่อคำตอบของบริการไม่เกิน 2 (รูปราคา 1 + ข้อความ 1) อยู่ในเพดาน 5 ของ LINE

วิธีแยก "ส่วนที่ใช้ร่วมกัน" กับ "ข้อความต่อท้ายต่อ OA" ในโค้ด (เช่น ให้ `messageTable` เก็บว่า trigger ไหนเป็นของบริการ `id` อะไร แล้วให้ฟังก์ชันประกอบคำตอบรับ `channelId`) เป็นของผู้สร้าง
ข้อบังคับคือ `chatRoute` และ preview ต้องใช้กติกาเดียวกันจากที่เดียว

## 8. หน้าจอหลังบ้าน (แบบ A)

เมนูใหม่ในแถบซ้าย **"ข้อความต่อท้าย"** ต่อจาก "Rich Menu" ใช้ CSS และ component ที่มีอยู่ (`PageHeader`, `UnsavedBar`, `FieldError`, ตาราง `.table`, `.card`)

### หน้า 1 — `#/followups`

- การ์ด **"ข้อความตั้งต้น"** คำอธิบาย: "ใช้กับ OA ที่ยังไม่ได้ตั้ง และ OA ใหม่ที่เพิ่มภายหลัง" ช่องพิมพ์หลายบรรทัด + ปุ่มบันทึกของตัวเอง (เรียก `PUT /followups/default`)
- ช่องค้นหา กรองตามชื่อหรือเลข OA
- ตาราง OA ทั้งหมดที่โหลดจาก `.env` เรียงตามเลข:
  - **LINE OA**: เลข + ชื่อ (`LINE_CHANNEL_NAME_<n>`) เป็นลิงก์ไปหน้า 2
  - **ข้อความของ OA**: ป้าย "ใช้ค่าตั้งต้น" / "ตั้งเอง" + ต้นข้อความ / "ไม่ส่ง"
  - **บริการที่ตั้งแยก**: จำนวนบริการที่ไม่ได้ "ใช้ของ OA" หรือ "—"
- หมายเหตุใต้ตาราง: เลข OA มาจาก `.env` ห้ามสลับเลข

### หน้า 2 — `#/followups/:id`

- breadcrumb "ข้อความต่อท้าย › <ชื่อ OA> (OA <เลข>)"
- การ์ด **"ข้อความของ OA นี้ (ทุกบริการ)"**: ตัวเลือก 3 ปุ่ม "ใช้ข้อความตั้งต้น / ตั้งข้อความเอง / ไม่ส่ง" เลือก "ตั้งข้อความเอง" แล้วมีช่องพิมพ์
- การ์ด **"แยกตามบริการ"**: ทุกบริการใน `services.json` ตามลำดับเดิม แสดงชื่อบริการ แต่ละแถวมีตัวเลือก "ใช้ของ OA / ตั้งข้อความเอง / ไม่ส่ง"
- ใต้ทุกช่องแสดง **ข้อความที่บอทจะส่งจริง** คำนวณสดจากสิ่งที่กำลังแก้ (ยังไม่บันทึกก็เห็น): กรอบเขียว "บอทส่ง: …" หรือกรอบแดง "บอทไม่ส่งข้อความนี้"
  - บริการที่ไม่มีรูปราคาและผลคือไม่ส่ง ต้องเขียนให้ชัดว่า "บอทไม่ตอบปุ่มนี้ใน OA นี้"
- ปุ่มบันทึกเดียว (เรียก `PUT /followups/channels/:id`), เตือนเมื่อออกจากหน้าโดยยังไม่บันทึก แบบเดียวกับหน้าอื่น (`dirtyState`)
- ข้อผิดพลาดจากการตรวจแสดงใต้ช่องที่ผิด

### หน้าที่มีอยู่แล้วที่ต้องแก้ข้อความ

- `ServiceEditPage.jsx` คำเตือนตอนไม่มีรูปราคา: เปลี่ยนจาก "บอทจะตอบข้อความ 'ปรึกษาหมอได้เลย หมอตอบเองครับ' อย่างเดียว" เป็นบอกว่าบอทจะตอบเฉพาะข้อความต่อท้ายของแต่ละ OA และ OA ที่ตั้ง "ไม่ส่ง" จะไม่ตอบปุ่มนี้
- `ServiceEditPage.jsx` ใต้ช่อง `id`: เตือนเรื่องเปลี่ยน `id` แล้วข้อความต่อท้ายที่ตั้งแยกจะหาย
- `ServicesPage.jsx` ป้าย "ตอบข้อความอย่างเดียว" ให้ยังถูกต้องกับกติกาใหม่

## 9. เทสต์ (`node --test`, ไม่เพิ่ม dependency)

อย่างน้อยต้องครอบ:

- กติกาเลือกข้อความ: ทั้ง 3 ระดับ, `""` หยุดที่ระดับนั้นไม่ไหลต่อ, ข้อความที่มีแต่ช่องว่าง = ไม่ส่ง, OA ที่ไม่มีในไฟล์ใช้ค่าตั้งต้น, `id` บริการที่ไม่มีอยู่ไม่ทำให้ล้ม
- webhook: OA 1 ได้ข้อความหมอ, OA อื่นได้ข้อความตั้งต้น, OA ที่ "ไม่ส่ง" ได้แค่รูปราคา, บริการไม่มีรูป + ไม่ส่ง → ไม่เรียก `replyMessage`, ไฟล์เสีย → ตอบรูปราคาโดยไม่มีข้อความต่อท้าย
- API: GET ไม่มี token/secret, PUT default, PUT OA ไม่แตะ OA อื่น, OA ที่ไม่ได้โหลด → 404, ข้อมูลผิด → 400 พร้อม path, ตัด `id` บริการที่ไม่มีอยู่, ข้อความว่างเปล่าถูกเก็บเป็น `""`
- บันทึกบริการที่ลบหรือเปลี่ยน `id` → ค่าของ `id` เดิมหายจากทุก OA
- preview ตาม `channel`
- แก้เทสต์เดิมใน `test/messageTable.test.js` ที่อ้าง `FOLLOW_UP_TEXT`; fixture `test/fixtures/menu-messages.json` ไม่ควรต้องเปลี่ยน

## 10. เอกสารและการ deploy

- อัปเดต CLAUDE.md (ส่วน `data/*.json`, `messageTable`, `chatRoute`, admin API, "Adding or changing content", "Adding a LINE OA" — OA ใหม่ใช้ข้อความตั้งต้นเอง, จำนวนเทสต์) และ README ส่วนหลังบ้าน
- `data/followups.json` เป็นไฟล์ข้อมูลที่แก้สดบนเซิร์ฟเวอร์ ข้อควรระวังเรื่อง deploy ใน CLAUDE.md ใช้กับไฟล์นี้ด้วย
- deploy ครั้งแรก: ไฟล์ใหม่ต้องขึ้นไปพร้อมโค้ด, `npm run admin:build`, restart server

## 11. สิ่งที่ผู้สร้างตัดสินใจเองได้

- ชื่อไฟล์/ฟังก์ชัน/โมดูล และการแยกโค้ด (ข้อบังคับคือกติกาเลือกข้อความอยู่ที่เดียว ใช้ทั้ง webhook และ preview)
- รูปแบบ response ของ GET/PUT ตราบที่ไม่มี token/secret และหน้าจอทำงานตามข้อ 8 ได้
- วิธีจำกัด log ตอนไฟล์เสีย
- หน้าตาของตัวเลือก 3 ปุ่ม และความยาวต้นข้อความในตาราง
- หน้าจอคำนวณ "ข้อความที่บอทจะส่งจริง" เองฝั่ง browser ได้ (ต้องให้ผลตรงกับกติกาฝั่ง server)

## 12. สิ่งที่ผมเลือกเอง (ผู้ใช้ยังไม่ได้ยืนยันทีละข้อ)

- ผูก OA ด้วยเลขใน `.env` และผูกบริการด้วย `id` ของบริการ
- ไม่มีระดับ "ข้อความของบริการที่ใช้ทุก OA"
- "ตั้งข้อความเอง" แต่ว่าง = ไม่ส่ง
- ข้อความยาวได้ไม่เกิน 5,000 ตัวอักษร
- เก็บค่าของ OA ที่ถูกเอาออกจาก `.env` ไว้ และลบค่าของบริการที่ถูกลบ/เปลี่ยน `id`
- บันทึกทีละส่วน (ข้อความตั้งต้น / ทีละ OA) แทนการบันทึกทั้งไฟล์ เพื่อไม่ให้ทับงานของคนที่แก้สาขาอื่นพร้อมกัน
- ไฟล์เสีย → ตอบโดยไม่มีข้อความต่อท้าย (ไม่ใช้ข้อความสำรองในโค้ด) และไม่ยอมให้บันทึกทับจนกว่าจะมีคนแก้ไฟล์
- preview ที่ไม่ระบุ OA ใช้ OA แรก (Main)
- ตัดช่องว่างหัวท้ายข้อความก่อนบันทึก และเอา OA ที่ไม่ได้ตั้งอะไรเลยออกจากไฟล์
- สองคนแก้ OA เดียวกันพร้อมกัน คนบันทึกทีหลังชนะ
- **ผูก OA ด้วยเลขใน `.env` ไม่ใช่ LINE user ID ของ OA** — ผู้ตรวจชี้ว่าข้อนี้ถ้าเปลี่ยนทีหลังจะกระทบมากที่สุด (key ในไฟล์, path ของ API, คำเตือนเรื่องห้ามสลับเลข)
  ที่เลือกเลข `.env` เพราะเป็นตัวเดียวกับที่หน้า Rich Menu ใช้ และรู้ได้ตั้งแต่เปิดแอปโดยไม่ต้องถาม LINE
  ส่วน user ID ของ OA ต้องดึงจาก LINE ตอนเปิดแอป ถ้า LINE ตอบไม่ได้ในตอนนั้นระบบจะไม่รู้ว่า OA ไหนเป็นของสาขาใด
